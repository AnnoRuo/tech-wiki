## 异常

在异常处理理论中，有两种基本模型：

- **终止模型**（termination）：假设错误是如此严重，程序无法返回到异常发生的位置继续执行。异常被抛出后，出错的方法就此终结，无法恢复。
- **恢复模型**（resumption）：异常处理程序有望通过某些工作来修正这种情况，处理完成后重新回到出错的方法中重试，使程序从异常点继续运行。

Java 支持**终止模型**（termination）。如果想在 Java 中获得类似恢复模型的行为，那么：

1. 当遇到错误时不要抛出异常，而是要调用某个能修复这个问题的方法
2. 把我们的`try`块放在一个`while`循环中，不断地重新进入这个`try`块，直到结果令人满意。

检查型异常实际上是 Java 的发明，然而，这只是一次尝试，之后的编程语言并没有采用这样的做法。


> 错误码 VS 异常
> 
> 在异常机制出现之前，程序通常通过返回错误码（error code）来报告问题，两者的对比如下：
> - 错误处理是否为强制的
> 	- 错误码：依赖调用者自觉检查返回值。一旦忘记检查，错误就会被悄无声息地吞掉，程序带着错误状态继续运行
> 	- 异常：无法被忽略。异常抛出后，如果未被捕获，它会沿调用栈一直向上传播，最终终止程序，并记录堆栈轨迹
> - 错误处理与业务逻辑的耦合程度
> 	- 错误码：检查代码必须紧跟在每次调用之后，错误处理逻辑与正常业务逻辑耦合在一起，可读性差
> 	- 异常：正常流程写在 `try` 块中，错误逻辑集中在 `catch` 块中
> - 错误的传播链
> 	- 错误码：只能逐层向上返回。如果错误需要跨越多个调用层才能到达有能力处理它的地方，中间每一层都必须透传错误码，层层加判断，代码臃肿
> 	- 异常：自动沿调用栈传播，中间层无需任何代码，可以跳过不关心该错误的层次，直接到达合适的错误处理程序
> - 错误所携带的报错原因
> 	- 错误码：通常只是一个整数，具体含义要查文档
> 	- 异常：是一个完整的对象，可以携带任意上下文信息（错误消息、堆栈轨迹、自定义字段），还可以通过类型体系对错误进行分类

### 异常的层次

https://rollbar.com/wp-content/uploads/2021/07/java-exceptions-hierarchy-example.png

- Throwable：所以异常的基类
- Error：程序无法处理的严重问题，通常由 JVM 或运行环境本身抛出，而不是应用程序代码抛出的


| Error                  | 含义                |
| :--------------------- | :---------------- |
| `OutOfMemoryError`     | 堆内存耗尽，JVM 无法再分配对象 |
| `StackOverflowError`   | 调用栈溢出，常见于无限递归     |
| `NoClassDefFoundError` | 编译时类存在，运行时找不到     |
| `LinkageError`         | 类链接失败（如类文件被改动）    |
| `VirtualMachineError`  | JVM 自身崩溃或资源耗尽的基类  |
